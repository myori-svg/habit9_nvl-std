# [AM-01] Auto Mode 파이프라인 (①DQ → ②구도 → ④장면 이미지)

## 상태
완료 — **배포 후 프로덕션 도메인에서 최종 확인 필요** (아래 "확인 필요" 참고)

## 카테고리
Auto Mode

## 목표 (원래 계획에서 범위 조정)
Manual Mode의 "Gemini에 복사해서 붙여넣기 → 결과 다시 붙여넣어 저장" 수동
과정을, Gemini API 직접 호출 + 기존 저장 방식 그대로 재사용하는 자동
파이프라인으로 대체.

사용자 지시로 ①DQ 생성 → ②구도 프롬프트 → ④장면 이미지 3장(본문/Option
A/Option B)만 먼저 이어지는 파이프라인으로 구성 — **③ 캐릭터 관리 단계는
이번 자동 파이프라인에서 의도적으로 제외** (한 번 세팅하면 계속 재사용하는
성격이라, 챕터마다 반복되는 ①②④와 달리 매번 자동으로 다시 돌 필요가 없음).

## 원래 계획과 달라진 점
- 원래 계획은 "SSE 스트리밍으로 단계별 진행"(setup-novel처럼)이었으나,
  실제로는 CharPromptStep/CharImageStep에 이미 있던 "클라이언트에서 순차
  루프 + AutoGenStatusList로 진행상황 표시" 패턴을 그대로 재사용함. 새
  스트리밍 엔드포인트를 안 만들어도 되고, 항목별 재시도/중지가 자연스럽게
  됨.
- 장면 이미지 저장 구조를 새로 설계함 (`DiscussionQuestion.sceneImages`:
  `main`/`optionA`/`optionB` 3슬롯, 각각 Firebase Storage URL). 기존
  DQ당 이미지 1장짜리 구조(`sceneImage`/`sceneImageUrl`)는 과거 저장된
  문서 호환용으로만 타입에 남겨둠 (deprecated 표시).
- 구도 프롬프트가 실제로 "본문 --- Option A --- Option B" 3구간 구조로
  나온다는 걸 확인하고, 이 구조를 그대로 분리해서(`splitCompositionScenes`)
  구간별로 캐릭터 감지 + 이미지 생성.

## 구현
- `lib/prompts.ts`: `splitCompositionScenes()` — 구도 프롬프트를 3구간으로
  분리
- `lib/firestore.ts` / `lib/store.ts`: `saveDQSceneImage()` — 슬롯별
  Storage 업로드 + Firestore 저장. `setPartDQs()`가 생성된 DQ 목록(id
  포함)을 반환하도록 변경 (`useStore.getState()` 직접 호출 금지 규칙 때문에
  — 방금 생성한 DQ의 id를 컴포넌트가 바로 이어서 쓸 수 있게)
- `components/WorkPanel.tsx`: 전면 재작성. 챕터 선택 → "전체 자동 생성"
  버튼 하나로 ①②④ 이어서 실행, DQ별 카드에 3장 이미지 + 개별 재생성 버튼
- 캐릭터 참고 이미지가 in-memory에서 날아간 경우(새로고침 등)
  `imageUrl`에서 다시 받아오는 fallback 추가 (`resolveCharImage`)
- Firebase Storage 업로드가 응답 없이 무한 재시도에 빠지는 경우가 있어서
  (아래 참고) `lib/withTimeout.ts` 공용 타임아웃 유틸 추가, 저장 실패 시
  항목별로 에러 처리하고 다음 항목으로 계속 진행

## 확인 필요 (중요)
로컬(`localhost:3000`)에서 실제 파이프라인을 끝까지 돌려보니 Gemini
생성(DQ/구도/장면 이미지)까지는 전부 실제로 잘 됐는데, **Firebase Storage
업로드 단계에서 CORS 에러로 막힘** (`Access to XMLHttpRequest ... blocked
by CORS policy`, origin `localhost:3000`). Storage 업로드가 실패를
던지지 않고 계속 재시도만 해서 무한 대기처럼 보였음 — 이번에 추가한
타임아웃으로 최소한 멈추지는 않게 해뒀지만, 근본 원인(CORS 설정)은 로컬
환경 특성일 수도 있고 아닐 수도 있어서 배포 후 실제 도메인에서 한 번
돌려봐야 함.

**더 중요한 발견**: 이 과정에서 기존 프로덕션 데이터를 확인해보니, 실사용
중인 "BGF" 소설의 캐릭터 5명 전부 `imageGenerated: true`인데
`imageUrl`이 하나도 없음 — 즉 캐릭터 이미지 자동 생성 버튼을 눌러도 지금껏
실제 이미지가 Storage에 한 번도 정상 저장된 적이 없었던 것으로 보임
(CharImageStep.tsx가 `updateCharacter`만 호출하고 `saveCharImage`를 안
불러서 생긴 기존 버그 — 이번에 고침). 이게 CORS 때문인지, 그냥 버그
때문에 애초에 시도조차 안 됐던 건지는 이 버그가 고쳐진 채로 프로덕션에서
한 번 눌러봐야 확실히 알 수 있음.

**요청**: 배포되면 아무 소설이나 골라서 ③-3 캐릭터 이미지 자동 생성을
한 번 눌러보거나, Auto Mode에서 "전체 자동 생성"을 한 번 돌려보고 이미지가
실제로 뜨는지 확인 부탁드려요. 안 뜨면 Firebase Storage 버킷의 CORS 설정에
배포 도메인이 허용되어 있는지 봐야 해요 (`gsutil cors set` 필요 — 제겐
그 프로젝트의 GCP 접근 권한이 없어서 직접 확인/설정을 못 함).
